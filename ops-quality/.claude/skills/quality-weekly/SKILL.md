# quality-weekly

업무 규칙(역할, 우선순위, 반복 기준, 중복 집계 금지, 표기, 제약)은 프로젝트 `CLAUDE.md`를 따른다. 여기에는 실행 순서와 단계별 완료 조건만 적는다.

**흐름:** 자료 읽기 → 기준 대조 → 이슈 식별 → 초안 작성 → 검증 → 검증 결과 저장 → 결과 보고

## 1. 자료 읽기
- `README.md`에서 기준일과 Pass 기준을 확인하고, `CLAUDE.md`를 읽는다.
- `data/불량보고/*.md`를 전부 읽는다. 날짜는 파일 이름에서 가져온다.
- 원본은 읽기만 한다.

## 2. 기준 대조
- 원본을 README의 Pass 기준과 `CLAUDE.md` 표기 규칙에 비춰 확인한다.
  - 보고 건수
  - 빈 원인(`원인 미기재` 대상), 빈 조치(`조치 미기재` 대상)
  - 조치 상태별 건수
  - 표기가 갈리는 유형(예: 스크래치/긁힘)
- 결과를 사용자에게 한 줄로 알린다. 기준이 불명확하면 진행하기 전에 질문한다.

## 3. 이슈 식별
`CLAUDE.md`의 판단 기준으로 이슈 그룹을 나눈다.
- 그룹: 기록 누락 / 반복 원인 / 반복 유형 / 그 외
- 보고 1건은 그룹 하나에만 넣는다. 그룹별 합계가 전체 보고 건수·불량 수량과 같은지 확인한다.
- 미조치 건은 조치 중 / 조치 완료 / 조치 미기재로 나눠 센다.

## 4. 초안 작성

### 4-1. 주간 보고서 → `report/품질주간.md`
- `CLAUDE.md`의 D트랙 공식 형식(요약 3줄 · 유형별 표 · 확인 필요 항목)을 지킨다.
- 기존 `report/품질주간.md`의 구조를 그대로 템플릿으로 쓴다. `verify.py`는 이 형식을 읽는다.
  - `## 1. 요약` ~ `## 6. 확인 필요 항목`. 장 번호와 제목은 유지한다.
  - 2장 유형별, 3장 라인별, 4장 원인별 표: 1열 항목, 2열 보고 건수, 3열 불량 수량. 마지막 행은 `**합계**`
  - 5장 미완료 조치 표의 열: 날짜(`MM-DD`) · 라인 · 유형 · 수량(`N개`) · 원인 · 조치 상태
  - 요약에 넣을 문구: `보고 **N건**, 불량 수량 **M개**`, `완료된 조치는 N건`
  - 5장 표 아래에 넣을 문구: `미완료 N건(조치 중 X건, 조치 미기재 Y건)`
- 집계를 바꿀 수 있는 판단(예: 유형 표기 통일)은 하지 않고, 판단이 필요하다는 메모만 남긴다.
- 작성 직후 **5-1 집계 검증**을 실행한다. FAIL이면 4-2와 5-2를 건너뛰고 6단계로 간다.

### 4-2. 조치 요청 초안 → `report/조치요청초안.md`
5-1이 PASS일 때만 작성한다.
- 기존 `report/조치요청초안.md`가 있으면 그 구조를 따른다.
  1. 주요 이슈 요약
  2. 우선 조치 항목
     - 2-1 이슈 그룹별 순위
     - 2-2 보고 건별 내역
     - 2-3 이슈별 확인 및 요청 사항
  3. 반복 이슈
     - 3-1 반복 발생
     - 3-2 미조치
  4. 라인별 조치 요청 메시지
  5. 담당자 검토 체크리스트
- 2-3의 이슈마다 네 가지를 적는다.
  - 확인된 사실 **[원본]**
  - 추가 확인이 필요한 사항
  - 요청할 조치 **[AI 제안]**
  - 회신 시 필요한 정보 **[AI 제안]**
- 수신자와 회신 기한은 `[확인 필요]`로 둔다. 메시지는 파일에 초안으로만 쓰고 발송하지 않는다.

## 5. 검증

### 5-1. 집계 검증: 주간 보고서
```
python scripts/verify.py
```
- `결과: PASS`이면 4-2로 넘어간다.
- `결과: FAIL`이면 **후속 문서 작성을 멈춘다.** `report/조치요청초안.md`는 만들거나 고치지 않는다.
  - FAIL 항목과 기대값을 그대로 기록한다.
  - 원인이 보고서 작성 오류라면 4-1로 돌아가 고친 뒤 다시 검증한다.
  - 원인이 원본 형식이나 스크립트 쪽이라면 고치지 말고 사용자에게 알린다.
- `verify.py`는 수정하지 않는다. 조치 요청 초안 검증에는 쓰지 않는다.

### 5-2. 사실성 검토: 조치 요청 초안
`report/조치요청초안.md`의 문장을 원본과 대조해 세 가지로 구분한다.
- **원본 사실:** 원본 필드(날짜·라인·유형·수량·원인·조치 상태)에 실제로 있는 내용
- **AI 제안:** `[AI 제안]`으로 표시된 요청·회신 항목
- **근거 없는 추론:** 원본에 없는데 사실처럼 쓴 내용

확인할 것:
- **[원본]**으로 표시한 내용이 원본에 실제로 있는지
- **시간 추론.** 원본에는 조치 상태가 언제 기록되거나 바뀌었는지가 없다.
  - "~가 조치 중인 상태에서 재발" 같은 문장을 쓰지 않는다.
  - 조치 상태는 "보고서 기록상"으로 쓴다.
  - "이번 주" 같은 상대 표현 대신 날짜 범위(`MM-DD ~ MM-DD`)로 쓴다.
- 원본에 없는 원인, 조치 결과, 담당자, 기한이 사실처럼 쓰였는지
- 숫자가 5-1에서 PASS를 받은 `report/품질주간.md`와 같은지

근거 없는 추론은 해당 문장만 최소한으로 고친다. 고친 뒤에도 남은 문제가 없으면 PASS, 사용자 판단 없이는 고칠 수 없는 문제가 남으면 FAIL이다.

## 6. 검증 결과 저장 → `report/검증결과.md`
실행할 때마다 덮어쓴다. 아래 항목만 간결하게 기록한다.

```markdown
# 검증 결과

- 실행일: YYYY-MM-DD (기준일: YYYY-MM-DD)
- 최종 결과: PASS | FAIL

| 검증 대상 | 방법 | 결과 | 실패 사유 |
|---|---|---|---|
| report/품질주간.md | scripts/verify.py | PASS/FAIL | FAIL 항목과 기대값, 없으면 - |
| report/조치요청초안.md | 사실성 검토 | PASS/FAIL/미실행 | 남은 문제 또는 "집계 검증 FAIL로 미실행", 없으면 - |

## 사실성 검토에서 고친 문장
- 수정 전 → 수정 후 (이유). 없으면 "없음"

## 확인 필요 사항
- `[확인 필요]` 항목, 사용자 판단이 필요한 [AI 제안], 표기 기준 등
```

- **최종 결과는 두 검증 대상이 모두 PASS일 때만 PASS다.** 하나라도 FAIL이거나 미실행이면 FAIL이다.

## 7. 결과 보고
사용자에게 짧게 보고한다. 최종 결과는 `report/검증결과.md`와 같게 쓰고, FAIL을 PASS로 보고하지 않는다.
- 최종 결과(PASS/FAIL)와 실패 사유
- 생성하거나 수정한 파일
- 핵심 수치: 보고 건수/불량 수량, 조치 상태별 건수, 1순위 이슈
- 5-2에서 고친 문장
- 확인 필요 사항
