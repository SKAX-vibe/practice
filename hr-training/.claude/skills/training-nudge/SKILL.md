# training-nudge

업무 규칙(역할, 기한, 신규 입사자 판별, 지연, 기한 후 수료, 확인 필요, 독려 대상, 공식 보고서 형식, 표기, 제약)은 프로젝트 `CLAUDE.md`를 따른다. 여기에는 실행 순서와 단계별 완료 조건만 적는다.

**흐름:** 자료 읽기 → 기준 대조 → 대상 식별 → 초안 작성 → 검증 → 검증 결과 저장 → 결과 보고

## 1. 자료 읽기
- `README.md`에서 기준일과 Pass 기준을 확인하고, `CLAUDE.md`를 읽는다.
- `data/직원명단*.csv`(전부), `data/교육과정.csv`, `data/수료기록.csv`를 읽는다.
- 원본은 읽기만 한다.

## 2. 기준 대조
원본을 README의 Pass 기준과 `CLAUDE.md`에 비춰 확인한다.
- 명단 인원, 과정 수, 과정별 기한과 신규 입사자 기한
- 명단 외 사번, 같은 사번·과정의 중복 수료 기록, 교육과정.csv와 다르게 적힌 과정명
- 신규 입사자(`입사일 + 30일`이 과정 기한보다 늦은 직원)와 판별 불명확(입사일 공란·날짜 아님·기준일 이후)
- 수료일이 기한보다 늦은 기록

결과를 사용자에게 한 줄로 알린다. 과정명이 다르게 적혀 있거나 중복 기록이 있으면 진행하기 전에 질문한다.
판별 불명확한 직원은 신규 여부를 정하지 않고 `확인 필요`로 두고 진행한다.

## 3. 대상 식별
- 과정마다 명단 전원을 이수 / 미이수(지연 · 기한 전 · 확인 필요)로 나눈다. 이수 + 미이수 = 명단 인원인지 확인한다.
- 이수 중 기한 후 수료를 따로 센다.
- 독려 대상 = 지연 인원. 사번별로 미이수 과정을 묶는다. 기한 전, 확인 필요, 명단 외 사번은 제외한다.

## 4. 초안 작성

### 4-1. 이수 현황 → `report/교육이수.md`
- `CLAUDE.md`의 B트랙 공식 형식(부서별 이수율 표 → 미이수자 목록)을 지킨다.
- 기존 보고서 구조를 그대로 템플릿으로 쓴다. `verify.py`는 이 형식을 읽는다.
  - 장 제목: `## 1. 부서별 이수율`, `## 2. 미이수자 목록`, `## 3. 확인 필요 항목`. 번호와 제목을 바꾸지 않는다.
  - 머리 문구: `미이수 연인원 **N명**(실인원 M명)`, `지연 **N명**(실인원 M명)`
  - 1장 표 열: 과정 · 부서 · 대상 · 이수 · 미이수 · 이수율 · 지연 · 기한 전 · 확인 필요 · 기한 후 수료. 부서는 명단 순서, 과정마다 마지막에 부서 `**전체**` 행
  - 2장 표 열: 과정 · 사번 · 이름 · 부서 · 입사일 · 기한(`MM-DD` 또는 `확인 필요`) · 기한 기준(`과정 기한`/`신규 입사자`/`확인 필요`) · 상태(`지연`/`기한 전`/`확인 필요`)
  - 3장 표 열: 구분 · 사번 · 과정 · 내용. 구분은 `명단에 없는 사번`, `기한 후 수료`, `신규 입사자 판별 불명확`, `과정명 불일치`, `명단 중복 불일치`. 명단 중복은 과정 칸에 `-`. 표 아래에 확인 필요 사항을 번호로 적고, 신규 입사자 판별 기준이 담당자 확정 전이라는 점을 남긴다.
- 작성 직후 **5-1 집계 검증**을 실행한다. 보고서 항목이 FAIL이면 4-2와 5-2를 건너뛰고 6단계로 간다.

### 4-2. 독려 초안 → `outbox/drafts/독려_<사번>.md`
- 지연 인원마다 하나씩 쓴다. 기존 초안 하나를 템플릿으로 쓴다.
  - `## 2. 미이수 내역` 표 열: 과정 · 기한 · 경과 일수 · 상태
- 독려 대상이 아닌 사번의 초안이 남아 있으면(이수했거나 기한 전으로 바뀐 경우) 지우지 말고 사용자에게 알린다.
- 연락처와 새 이수 기한은 `[확인 필요]`로 둔다. 발송하지 않는다.

## 5. 검증

### 5-1. 집계 검증
```
python scripts/verify.py
```
- 보고서 항목과 독려 초안 항목을 모두 확인한다. `결과: PASS`이면 5-2로 넘어간다.
- `결과: FAIL`이면 FAIL 항목과 기대값을 그대로 기록한다.
  - 원인이 보고서·초안 작성 오류라면 4단계로 돌아가 고친 뒤 다시 검증한다.
  - 원인이 원본 형식이나 스크립트 쪽이라면 고치지 말고 사용자에게 알린다. 5-2는 미실행으로 둔다.
- `verify.py`는 수정하지 않는다.

### 5-2. 사실성 검토: 독려 메시지
각 초안의 1장 메시지를 원본과 대조한다.
- 이름 · 사번 · 부서 · 과정 · 기한이 원본과 같은지
- "수강하지 않았다", "규정 위반" 같은 단정이나 원본에 없는 불이익·징계를 쓰지 않았는지. "수료 기록에서 확인되지 않음"으로 쓴다.
- 원본에 없는 새 기한, 교육 일정, 연락처를 사실처럼 쓰지 않았는지

문제 문장은 최소한으로 고친다. 사용자 판단 없이는 고칠 수 없는 문제가 남으면 FAIL이다.

## 6. 검증 결과 저장 → `report/검증결과.md`
실행할 때마다 덮어쓴다.

```markdown
# 검증 결과

- 실행일: YYYY-MM-DD (기준일: YYYY-MM-DD)
- 최종 결과: PASS | FAIL

| 검증 대상 | 방법 | 결과 | 실패 사유 |
|---|---|---|---|
| report/교육이수.md + outbox/drafts/독려_*.md | scripts/verify.py | PASS/FAIL | FAIL 항목과 기대값, 없으면 - |
| 독려 메시지 | 사실성 검토 | PASS/FAIL/미실행 | 남은 문제, 없으면 - |

## 사실성 검토에서 고친 문장
- 수정 전 → 수정 후 (이유). 없으면 "없음"

## 확인 필요 사항
- 명단 외 사번, 기한 후 수료 인정 여부, 신규 입사자 판별 기준, 연락처, 새 이수 기한 등
```

- **최종 결과는 두 검증이 모두 PASS일 때만 PASS다.**

## 7. 결과 보고
사용자에게 짧게 보고한다. 최종 결과는 `report/검증결과.md`와 같게 쓴다.
- 최종 결과(PASS/FAIL)와 실패 사유
- 과정별·부서별 이수율, 미이수 인원, 지연 인원(연인원·실인원)
- 독려 초안을 쓴 사번과 제외한 사번(기한 전, 확인 필요, 명단 외)
- 생성하거나 수정한 파일, 확인 필요 사항
